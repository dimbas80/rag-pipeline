# ADR-010: RAG v2 — семантические активы и токен-ориентированное чанкирование

**Статус:** предложено
**Дата:** 2026-08-05
**Исправлен:** 2026-08-05 (tokenizer Qwen3, --rag overwrite, таблицы всегда в image/)
**Заменяет:** ADR-009 (поля `source.page`, `max_chunk_chars`)

---

## Контекст

ADR-009 реализовал базовый RAG-контур: конвертацию структурированного Markdown в JSONL с метаданными
документа, иерархией разделов и кросс-ссылками. Однако после эксплуатации на реальных документах
(ГОСТ, СП, СО) выявились ограничения:

1. **Char-based чанкинг** (max_chunk_chars=1500) не отражает реальную ёмкость embedding-модели
   (окно 8000 токенов, тест 512 дал неудовлетворительное качество, рабочий потолок — 7000 токенов).
2. **Номера страниц в публичной схеме** (`source.page`) — это внутренняя деталь OCR, не имеющая
   смысла для пользователя RAG; ссылки должны вести на логические пункты/таблицы/изображения.
3. **Отсутствует реестр активов** — таблицы и изображения не зарегистрированы как отдельные сущности,
   невозможно связать чанк с его визуальными активами.
4. **Статус документа** не передаётся в чанки — RAG-поиск не может отфильтровать недействующие документы.
5. **Риск повторной генерации** — `--rag` запускается внутри process_file() вместе с OCR, что может
   привести к перезаписи проверенного человеком Markdown.

> **Исправление (2026-08-05):** Первоначально ADR-010a выбрал `tiktoken cl100k_base` как токенизатор.
> Однако фактическая embedding-модель проекта — `Qwen3-Embedding-8B` (через SiliconFlow API).
> Токенизатор должен совпадать с embedding-моделью, чтобы подсчёт токенов был точным. Решение
> пересмотрено: использовать Qwen3-native токенизатор через `transformers.AutoTokenizer`.

---

## Решения

### ADR-010a: Tokenizer-based чанкинг (Qwen3-Embedding-8B native tokenizer)

**Решение:** Подсчитывать токены через родной токенизатор embedding-модели
`Qwen/Qwen3-Embedding-8B`, загружаемый через `transformers.AutoTokenizer`.

**Параметры:**
```yaml
defaults:
  max_chunk_tokens: 7000                # рабочий потолок, запас 1000 до окна 8000
  tokenizer: "Qwen/Qwen3-Embedding-8B"  # HF model id для AutoTokenizer
  tokenizer_revision: "main"            # фиксированная ревизия (опционально)
  allow_degraded_fallback: false        # запретить молчаливый chars/token fallback
  tokenizer_fallback_ratio: 3.5         # chars/token только при явном allow_degraded_fallback: true
```

**Загрузка токенизатора:**
```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(
    "Qwen/Qwen3-Embedding-8B",
    revision="main",           # фиксированная ревизия
    local_files_only=False,    # первый раз скачать, затем cache
    trust_remote_code=False,   # Qwen2Tokenizer встроен в transformers >= 4.51.0
)
```

**Технические детали:**
- Tokenizer class: `Qwen2Tokenizer` (Qwen3 переиспользует токенизатор Qwen2 без изменений)
- Требует `transformers >= 4.51.0`
- Размер файлов токенизатора: ~3-5 МБ (tokenizer.json, vocab.json, merges.txt, tokenizer_config.json)
- Кеширование: стандартный HuggingFace cache (`~/.cache/huggingface/hub/`)
- После первой загрузки можно использовать `local_files_only=True` для офлайн-режима
- Подсчёт токенов: `len(tokenizer.encode(text))` — максимально точный, совпадает с embedding-моделью

**Стратегия при недоступности токенизатора:**

1. `transformers` не установлен → **ошибка**, RAG отказывается запускаться.
   ```
   log.error("transformers не установлен — RAG-индексация невозможна. Установите: pip install transformers>=4.51.0")
   ```

2. Токенизатор не удалось загрузить (сеть/HF недоступен, нет в кеше) → **ошибка**, RAG отказывается запускаться.
   ```
   log.error("Не удалось загрузить токенизатор Qwen/Qwen3-Embedding-8B — RAG-индексация невозможна")
   ```

3. **Degraded fallback (chars/token) допускается ТОЛЬКО** если явно включён в `rag_config.yaml`:
   ```yaml
   defaults:
     allow_degraded_fallback: true   # ЯВНОЕ согласие на деградацию
   ```
   При включённом fallback:
   - `log.warning("Работаю в деградированном режиме: chars/token={ratio}")`
   - В каждую JSONL-строку добавляется `"chunking_method": "degraded_chars_per_token"`
   - `chunk_tokens` — приблизительная оценка, не точный подсчёт

**Rationale:**
- Точность: Qwen3 tokenizer даёт 100% точный подсчёт токенов для embedding-модели
- tiktoken `cl100k_base` имеет другую токенизацию (BPE для GPT-семейства vs Qwen BPE) —
  расхождение может достигать 30% на русском тексте с формулами и спецсимволами
- `transformers` уже используется в проекте для других целей или легко добавляется
- Размер токенизатора (~5 МБ) сравним с tiktoken (~2 МБ)
- Явный отказ вместо молчаливого fallback исключает скрытые ошибки чанкирования
- Degraded fallback — осознанный выбор оператора, а не автоматическое поведение

**Отклонённая альтернатива (tiktoken cl100k_base):** Была выбрана в первоначальной версии ADR-010a
по критериям «pure Python, без нативных зависимостей, ~2 МБ». Однако после уточнения фактической
embedding-модели (`Qwen3-Embedding-8B` через SiliconFlow) выяснилось, что tiktoken использует
другой BPE-алгоритм (GPT-family, 100K vocab) и даёт расхождение в подсчёте токенов до 30%
на русских нормативных текстах. Это неприемлемо для точного чанкирования с лимитом 7000 токенов.

**Ссылки:**
- HuggingFace: https://huggingface.co/Qwen/Qwen3-Embedding-8B
- Tokenizer class: `Qwen2Tokenizer` (совместим с Qwen3, встроен в transformers >= 4.51.0)
- Токенизатор Qwen3 идентичен Qwen2, подтверждено в `tokenizer_config.json` (поле `tokenizer_class: "Qwen2Tokenizer"`)

### ADR-010b: Статус документа (active/inactive)

**Решение:** Добавить в `rag_config.yaml` секцию `documents.<slug>` поля:

```yaml
documents:
  so153_molniezashita:
    status: active                  # active | inactive
    status_reason: null             # причина неактивности (только для inactive)
    replaced_by_document_id: null   # номер/идентификатор заменившего документа (только для inactive), например "СП 60.13330.2012"
    replaced_by_doc_key: null       # опционально: ключ каталога (slug) заменившего документа
```

**Семантика:**
| status    | status_reason         | replaced_by_document_id   | replaced_by_doc_key | Смысл                                       |
|-----------|-----------------------|---------------------------|---------------------|----------------------------------------------|
| active    | null                  | null                      | null                | Действующий документ                         |
| inactive  | "Отменён приказом №N" | "СП 89.13330.2016"        | "sp89_kotelnye"     | Заменён другим документом                    |
| inactive  | "Утратил силу"        | null                      | null                | Отменён без замены                           |
| (отсутствует) | —                 | —                         | —                   | **Неизвестно** — трактовать как active с warning |

**Поле `status` попадает в каждую JSONL-строку** для фильтрации на стороне RAG-индекса:
```json
{"status": "active", ...}
```

**Поведение при неизвестном статусе:**
- Если поле `status` отсутствует в конфиге → `log.warning`, трактовать как `"active"`
- В JSONL всегда проставляется явное значение (не null)

**Rationale:**
- Два состояния (active/inactive) достаточно; более сложная машина состояний (draft/under_review/etc.)
  не нужна для нормативных документов
- `status_reason` и `replaced_by_document_id` — только для inactive, для active всегда null
- `replaced_by_doc_key` — опциональный ключ каталога, только при необходимости; не подменяет `replaced_by_document_id`
- Явное указание статуса в каждом чанке позволяет RAG-поиску фильтровать недействующие документы
  без дополнительного JOIN'а с конфигом

### ADR-010c: Удаление source.page из публичного JSONL

**Решение:** Убрать поле `source.page` из публичного JSONL-контракта. Сохранить page во
внутреннем поле `_source_page` (с префиксом `_` — соглашение о приватности) для отладки и
трассировки.

**Было (ADR-009):**
```json
{"source": {"file": "...", "page": 7}, ...}
```

**Стало (ADR-010):**
```json
{"source": {"file": "..."}, "_source_page": 7, ...}
```

**Новые поля-локаторы (вместо page):**
- `section_path`: строка вида `"3 → 3.2 → 3.2.1"` — путь по иерархии разделов
- `chunk_id`: уникальный идентификатор чанка, не зависящий от страниц:
  `"{doc_slug}/{clause_number}[/part_{N}]"` — например `"so153/3.2.1/part_1"`
- `heading_texts`: словарь `{"chapter": "3. ЗАЩИТА...", "section": "3.2. Внешняя...",
  "clause": "3.2.1. Молниеприемники"}` — человекочитаемые названия

**Дополнение (occurrence-суффикс chunk_id и embedding-контекст):**
- Повторный numbered top-level блок (напр. «## 1/2/3» в разделе рекомендаций после
  «## 1. ВВЕДЕНИЕ») сохраняет базовый ID только для первого вхождения; повторы
  получают детерминированный суффикс `/occurrence_{N}` (N = 2, 3, …) ДО `/part_{N}`.
  ID гарантированно уникальны в пределах одного результата `build_rag_jsonl_v2()`.
- Новое поле `embedding_text`: непустые заголовки из `heading_texts` в порядке
  `chapter → section → clause` с префиксами `Заголовок главы/раздела/пункта:`,
  затем пустая строка и исходный `text`. Публичное поле `text` не изменяется.
- Новое поле `embedding_tokens`: токены `embedding_text` (для лимита embedding-модели);
  `chunk_tokens` остаётся количеством токенов только `text`.

**Rationale:**
- Номера страниц PDF не имеют смысла для конечного пользователя RAG
- Логическая адресация (пункт/подпункт) соответствует тому, как люди ссылаются на нормативные документы
- `chunk_id` стабилен при пересборке (если пункт не менялся — ID тот же)
- Внутреннее `_source_page` сохранено для отладки (можно сопоставить чанк с исходным PDF)

### ADR-010d: Реестр активов rag_assets.json

**Решение:** При запуске `--rag` генерировать `rag_assets.json` — реестр всех таблиц и
изображений из финального Markdown.

**Схема:**
```json
{
  "document_id": "СО 153-34.21.122-2003",
  "doc_slug": "so153_molniezashita",
  "generated_at": "2026-08-05T12:00:00Z",
  "assets": {
    "tables": [
      {
        "asset_id": "so153/table/1",
        "caption": "Таблица 3.1 — Значения сопротивления заземлителей",
        "md_lines": [245, 278],
        "image_path": "image/table_1.png",
        "chunk_ids": ["so153/3.1"]
      }
    ],
    "images": [
      {
        "asset_id": "so153/fig/1",
        "caption": "Рис. 1 — Зона защиты молниеотвода",
        "image_path": "image/fig_1.png",
        "chunk_ids": ["so153/3.2.1"]
      }
    ]
  }
}
```

**Идентификация таблиц без страниц:**
- Таблицы детектятся в итоговом Markdown по Markdown-синтаксису (строки `|...|`)
- Каждой таблице присваивается `asset_id` = `"{doc_slug}/table/{N}"`, где N — порядковый
  номер таблицы в документе (сверху вниз)
- `md_lines` — диапазон строк в итоговом .md файле (для верификации и отладки)
- Связь с изображением: `image_path = "image/table_{N}.png"` (вырезанное изображение таблицы)

**Идентификация изображений:**
- Изображения детектятся по Markdown-ссылкам `![Рис. N](image/fig_N.png)`
- `asset_id` = `"{doc_slug}/fig/{N}"`
- Порядок — по появлению в Markdown

**Связь активов с чанками:**
- `chunk_ids` — список chunk_id, в чей текст попадает актив (таблица как Markdown) или
  ссылка на изображение
- Если чанк разбит (oversized clause) — актив связывается с тем подчанком, в который
  физически попал текст таблицы/изображения

**Разрешение путей:**
- Все пути в `rag_assets.json` — относительные, от директории итогового .md файла
- Приложение, использующее JSONL, разрешает пути относительно `rag_assets.json`

**Rationale:**
- Отдельный реестр позволяет RAG-приложению загрузить только метаданные активов без
  парсинга всего JSONL
- Связь asset → chunk_ids обеспечивает двунаправленную навигацию
- Стабильные ID (не зависят от страниц) гарантируют консистентность при пересборке

### ADR-010e: Трёхэтапный CLI и безопасный --rag

**Решение:** Явно разделить пайплайн на три этапа и гарантировать, что `--rag` не модифицирует
проверенный Markdown и не запускает повторное OCR/извлечение изображений.

**Этап 1 — Генерация (как сейчас):**
```bash
python3 create_markdown.py -i file.pdf            # без --ai: простой документ
python3 create_markdown.py -i file.pdf --ai       # с --ai: сложный документ
```
→ `Markdown/file/file.md` + `image/`

**Важное уточнение:** На этапе 1 таблицы **всегда** вырезаются в `image/table_N.png`,
независимо от флага `--ai`. `--ai` управляет только запуском vision/AI-коррекции
(исправление OCR-ошибок через LLM). Вырезание таблиц — локальная операция PyMuPDF,
которая не требует AI и выполняется всегда для любого PDF/DOCX.

**Этап 2 — Проверка человеком:**
- Человек открывает `file.md` и сверяет с исходным PDF
- При необходимости вносит правки в `file.md`

**Этап 3 — RAG-индексация (отдельный запуск):**
```bash
python3 create_markdown.py -i Markdown/file/file.md --rag
```
→ `Markdown/file/rag_chunks.jsonl` + `rag_assets.json`

**Гарантии безопасности `--rag` при входном .md:**
1. **НЕ запускает OCR** — Yandex API не вызывается
2. **НЕ извлекает изображения/таблицы заново** — только читает существующую `image/`
3. **НЕ модифицирует .md файл** — только читает его для построения JSONL
4. **Атомарно ПЕРЕЗАПИСЫВАЕТ** `rag_chunks.jsonl` и `rag_assets.json` — это производные
   данные, безопасно перезаписывать при каждом запуске; `.md` и `image/` не затрагиваются
5. Требует наличия `image/` в той же директории, что и .md (если нет — реестр активов пуст)

**Перезапись rag_chunks.jsonl и rag_assets.json:**
- При каждом запуске `--rag` оба файла создаются заново (атомарная перезапись)
- Это безопасно, так как:
  - Исходные данные (.md, image/) не модифицируются
  - JSONL и assets — полностью производимые из .md + image/ данные
  - Повторный запуск даёт идентичный результат (идемпотентность)
- Markdown-файл остаётся read-only на протяжении всей RAG-индексации

**Предотвращение вложенного Markdown/<file>/Markdown/<file>:**
- Если входной путь уже содержит `Markdown/` в пути — `process_file()` определяет, что это
  режим `.md + --rag` (не PDF/DOCX), и пропускает OCR
- Сигнатура `process_file()` проверяет `input_path.suffix == ".md"` И путь содержит `Markdown/` →
  режим RAG-only (без OCR, без постобработки, без модификации .md)

**Rationale:**
- Разделение этапов исключает риск случайной перезаписи проверенного Markdown
- Явный контракт: .md внутри Markdown/ + --rag = только индексация
- Перезапись JSONL/assets безопасна — это производные данные
- Не требуется отдельных скриптов — используется тот же create_markdown.py с другим режимом
- Вырезание таблиц всегда (без --ai) — уменьшает путаницу: таблицы в image/ появляются
  всегда, независимо от AI-обработки

### ADR-010f: chunk_id без страниц

**Решение:** Формировать chunk_id по шаблону:

```
{doc_slug}/{clause_number}[/occurrence_{N}][/part_{N}]
```

**Примеры:**
| Тип clause          | chunk_id                     |
|---------------------|------------------------------|
| Глава (## 3.)       | `so153/3`                    |
| Раздел (### 3.2.)   | `so153/3.2`                  |
| Пункт (#### 3.2.1.) | `so153/3.2.1`                |
| Подпункт (#####)    | `so153/3.2.1.1`              |
| Разбитый пункт      | `so153/3.2.1/part_1`         |
| Повторный пункт     | `so153/1/occurrence_2`       |
| Без номера          | `so153/_h7` (fallback: хеш)  |

**Fallback для ненумерованных заголовков:**
- Если `clause_number` = None → `chunk_id = "{doc_slug}/_h{idx}"` где idx — порядковый номер
  заголовка в пределах родительского раздела

**Уникальность (дополнение):** если один и тот же базовый `chunk_id` встречается повторно
(повторный numbered top-level блок, напр. «## 1/2/3» в разделе рекомендаций), первое
вхождение сохраняет базовый ID, а повторы получают `/occurrence_{N}` (N = 2, 3, …)
до `/part_{N}`. Суффикс детерминирован и не зависит от порядка обхода dict.

**Rationale:**
- Стабильность: ID не меняется при повторной обработке того же документа
- Человекочитаемость: по ID видно, о каком пункте идёт речь
- Отсутствие привязки к страницам: даже если PDF перевёрстан — ID не меняется

### ADR-010g: Стратегия разбиения больших таблиц

**Решение:** Таблицы в Markdown — атомарные объекты (не разбиваются). Если таблица превышает
`max_chunk_tokens` (7000 токенов = ~24 500 символов кириллицей):

1. Публикуется как отдельный чанк, даже если превышает лимит (с `log.warning`)
2. В поле `text` чанка: заголовок таблицы (caption) + Markdown-таблица
3. `chunk_id` получает суффикс `_table`: `"so153/3.1_table"`
4. В `section_path` добавляется `" → [Таблица 3.1]"`

**Для экстремально больших таблиц (> 14000 токенов, что маловероятно для ГОСТ):**
- Разбить таблицу по строкам с повторением заголовка в каждом подчанке
- Суффикс: `"so153/3.1_table/part_1"`, `"so153/3.1_table/part_2"`, ...

**Rationale:**
- ГОСТ-таблицы редко превышают 7000 токенов (типичная таблица 20×5 = ~2000 токенов)
- Разрыв таблицы ломает её семантику; атомарность предпочтительнее
- Экстремальный случай (гигантская таблица) обрабатывается явной стратегией с повторением заголовка

## Отклонённые альтернативы

### Альтернатива A: Сохранить page в публичной схеме

**Отклонено:** Противоречит явному требованию — «номера страниц не являются пользовательской
ссылкой». Page остаётся во внутреннем поле `_source_page`.

### Альтернатива B: Статус документа как булев флаг is_active

**Отклонено:** `status_reason` и `replaced_by_document_id` (официальный номер) дают контекст для пользователя RAG
(«этот документ заменён, смотрите СП 89.13330»). Булев флаг эту информацию теряет.

### Альтернатива C: Встроить asset-реестр в JSONL

**Отклонено:** Раздувает JSONL, смешивает chunk-level и document-level данные. Отдельный
`rag_assets.json` позволяет загрузить реестр активов один раз, не сканируя все чанки.

### Альтернатива D: Использовать tiktoken вместо Qwen3-native токенизатора

**Отклонено:** `tiktoken` использует BPE-алгоритм семейства GPT (encoding `cl100k_base`),
который не совпадает с токенизацией Qwen3. На русских нормативных текстах расхождение
может достигать 30%. Для точного чанкирования с лимитом 7000 токенов необходимо
использовать родной токенизатор embedding-модели. `transformers.AutoTokenizer` для
`Qwen/Qwen3-Embedding-8B` загружает только файлы токенизатора (~5 МБ), не требует
загрузки весов модели (8B параметров, ~16 ГБ).

### Альтернатива E: Молчаливый chars/token fallback при недоступном токенизаторе

**Отклонено:** Скрытая деградация точности чанкирования недопустима. Оператор должен явно
знать, что RAG работает в деградированном режиме. Fallback возможен только при сознательном
включении `allow_degraded_fallback: true` в конфиге и всегда виден в логах и метаданных JSONL.

## Последствия

### Положительные
- Токен-ориентированное чанкирование с точным подсчётом через Qwen3 tokenizer (100% точность)
- Статус документа позволяет фильтровать RAG-поиск (только действующие документы)
- Реестр активов даёт двунаправленную навигацию чанк ↔ таблица/изображение
- Трёхэтапный CLI исключает риск случайной перезаписи проверенного Markdown
- Стабильные chunk_id не зависят от перевёрстывания PDF
- Таблицы всегда вырезаются в image/ на этапе 1 (без путаницы с --ai)

### Отрицательные
- Новая зависимость: `transformers >= 4.51.0` (~5 МБ для файлов токенизатора)
- Требуется загрузка токенизатора с HuggingFace Hub при первом запуске (требуется сеть)
- `rag_assets.json` добавляет второй выходной файл (помимо JSONL)
- Обновление `rag_config.yaml` требует ручного добавления status для существующих документов
- Изменение публичного JSONL-контракта ломает обратную совместимость (поле `source.page`)

### Риски
- **Доступность HF Hub:** При первой загрузке токенизатора требуется доступ к
  huggingface.co. Решение: после первой загрузки использовать `local_files_only=True`,
  кешировать в HF_HOME. Для полностью офлайн-окружения — предварительно скачать файлы
  токенизатора.
- **Статус по умолчанию:** Если поле `status` отсутствует в конфиге, документ трактуется как
  active. Это безопасно (не теряем документы), но может пропустить недействующий документ в
  индекс, пока администратор не обновит конфиг.
- **Стабильность chunk_id:** Если администратор меняет `doc_slug` в конфиге, все chunk_id
  меняются. Решение: задокументировать, что slug — стабильный идентификатор, не подлежащий
  переименованию без полной переиндексации.
- **Деградированный fallback:** При явном включении `allow_degraded_fallback: true`
  точность чанкирования зависит от эвристики chars/token. Для русского текста с формулами
  погрешность может достигать 15-20%. Поле `chunking_method` в JSONL позволяет отличить
  degraded-чанки от нормальных.
