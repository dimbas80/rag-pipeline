# ADR-9: md_to_rag_jsonl — conversion of structured MD to RAG JSONL

**Статус:** предложено
**Дата:** 2026-08-01

---

## Проблема

После Этапа 1 (Yandex OCR → корректные `##`/`###`/`####`/`#####` заголовки — ADR-8) и постобработки получается хорошо структурированный Markdown. Его нужно преобразовать в формат, пригодный для RAG-индексации — строки JSONL, каждая из которых представляет clause (статью/пункт/подпункт) с полным контекстом (метаданные документа, иерархия разделов, ссылки).

Требования:
- Clause = единица индексации; текст ограничен следующим заголовком любого уровня
- Метаданные документа из `rag_config.yaml` повторяются в каждой строке
- Номера chapter/section/clause извлекаются из текста заголовка
- Номера страниц — из Yandex JSON (через `_extract_headings_from_json`)
- Кросс-ссылки извлекаются regexp-паттернами
- Oversized clause (> max_chunk_chars) разбиваются с повторением метаданных
- `ignore_sections` из конфига пропускаются целиком

---

## Решение

### ADR-9a: Clause boundaries = все заголовки (`##`–`#####`)

**Решение:** Каждый заголовок от `##` до `#####` порождает одну JSONL-строку. Текст clause — всё от строки заголовка (эксклюзивно) до следующего заголовка любого уровня (или конца файла).

**Rationale:**
- Главы (`##`) обычно содержат только вводный абзац перед первым разделом — их текст короткий и релевантный
- Разделы (`###`) аналогично — вводная часть перед первым clause
- Основной контент сконцентрирован на уровнях `####` и `#####`
- Такая структура сохраняет семантическую иерархию документа и позволяет RAG-поиску находить как общие положения (главы/разделы), так и конкретные пункты

**Поля в JSONL по уровням:**

| Уровень MD | chapter | section | clause |
|------------|---------|---------|--------|
| `## 3.`    | "3"     | null    | null   |
| `### 3.2.` | "3"     | "3.2"   | null   |
| `#### 3.2.1.` | "3"  | "3.2"   | "3.2.1" |
| `##### 3.2.1.1.` | "3" | "3.2" | "3.2.1.1" |

Для `#####` subclause использует поле `clause` (отдельное поле `subclause` не вводится — схема БД имеет только chapter/section/clause).

### ADR-9b: Разбиение oversized clause по границам параграфов

**Проблема:** Некоторые clause (особенно табличные) могут превышать `max_chunk_chars` (по умолчанию 1500). Нужно разбить, но сохранить целостность.

**Решение:**
1. Разбивать текст clause по двойным переносам строки (`\n\n`) — границам параграфов
2. Таблицы (строки, начинающиеся с `|`) и кодовые блоки (`````) не разрывать — считать атомарными
3. Каждый подчанок получает те же метаданные, что и исходный clause
4. В поле `clause` добавляется суффикс: `"3.2.1 (ч. 1)"`, `"3.2.1 (ч. 2)"`, ...
5. Если clause НЕ удалось разбить (одна гигантская таблица) — публикуется как есть с `log.warning`

**Rationale:** Границы параграфов — естественные семантические разрывы. Таблицы и код-блоки сохраняются целыми, чтобы не потерять структуру. Повторение метаданных в каждом подчанке гарантирует, что RAG-поиск найдёт любой подчанок независимо.

### ADR-9c: Heading-to-page mapping через existing `_extract_headings_from_json()`

**Проблема:** Нужно узнать номер страницы PDF для каждого clause. Yandex JSON содержит номера страниц для блоков, но парсить его заново неэффективно.

**Решение:** Повторно использовать `_extract_headings_from_json()` (ADR-8), которая уже возвращает `[{"page": N, "y": Y, "full_text": "...", "number": "3.2.1", ...}]`. Сопоставлять MD-заголовки с JSON-заголовками по `number` и `full_text`.

**Алгоритм:**
1. Вызвать `_extract_headings_from_json(pages)` → список heading-словарей
2. Построить индекс: `{number: page}` (первое вхождение)
3. Для каждого clause в MD — найти page по `number`
4. Если нет JSON (например, .md + --rag без OCR) — `source.page = null`

**Rationale:** `_extract_headings_from_json()` уже отлажена и протестирована на ГОСТ-документах. Повторное использование исключает дублирование кода и гарантирует консистентность.

### ADR-9d: Единый файл конфигурации `rag_config.yaml`

**Проблема:** Метаданные документов (document_id, title, edition, dates, source_file, ignore_sections) должны быть сконфигурированы один раз и переиспользованы.

**Решение:** Один YAML-файл `firmware/src/rag_config.yaml` с секциями:
- `defaults` — глобальные настройки (max_chunk_chars, include_tables, include_images, extract_references)
- `references.patterns` — regexp для извлечения кросс-ссылок
- `documents.<slug>` — per-document (document_id, title, edition, source_file, ignore_sections, ...)

**Поиск документа по slug:** `build_rag_jsonl()` принимает `doc_key` — slug из секции `documents`. Вызывающий код (`process_file()`) определяет slug по имени файла через `find_input_files()`.

**Rationale:** Структура уже специфицирована в `docs/software/rag_config_spec.yaml`. Соответствует подходу `config_ai.yaml` (ADR-5).

### ADR-9e: Интеграция в create_markdown.py как секция 12

**Решение:** Добавить секцию `12. RAG JSONL Converter` в `create_markdown.py` (~120 строк). Активируется флагом `--rag`.

**Позиция в pipeline:**
```
... → run_script_postprocess() → [--ai] ai_postprocess() → [--rag] build_rag_jsonl()
```

После постобработки (и AI если --ai), перед сохранением финального .md. RAG-конвертация работает с финальным Markdown, содержащим корректные заголовки.

**Флаг CLI:** `--rag` (булев). Опционально: `--rag-config` (путь к rag_config.yaml, default `./rag_config.yaml`).

**Rationale:** `--rag` логически независим от `--ai` — можно генерировать JSONL без AI-постобработки и наоборот. Позиция после всей постобработки гарантирует, что заголовки корректны, таблицы объединены, LaTeX очищен.

## Отклонённые альтернативы

### Альтернатива A: Отдельный скрипт `rag_converter.py`

**Отклонено:** Противоречит ADR-4 (один файл). Добавляет сложность с импортами и переиспользованием `_extract_headings_from_json()`. Pipeline-интеграция с `--rag` флагом проще для пользователя.

### Альтернатива B: Clause только на уровне `####`

**Отклонено:** Главы и разделы тоже содержат полезный текст (определения, область применения). Пропуск ##/### теряет контекст.

### Альтернатива C: Разбиение oversized clause через LLM

**Отклонено:** Избыточно для данной задачи. Границы параграфов — достаточная эвристика. LLM добавила бы стоимость и недетерминизм.

---

## Последствия

- **Положительные:** RAG-индексация интегрирована в pipeline, JSONL генерируется атомарно с конвертацией MD. Повторное использование `_extract_headings_from_json()` исключает дублирование.
- **Отрицательные:** `create_markdown.py` вырастет ещё на ~120 строк (до ~3170). Зависимость от `_extract_headings_from_json()` означает, что RAG требует наличия Yandex JSON (pages).
- **Риски:** Если Yandex JSON недоступен (режим .md + --rag) — `source.page` будет null, но JSONL всё равно генерируется. Regexp для извлечения номеров chapter/section/clause из текста заголовка должен быть устойчив к нестандартным форматам нумерации (римские цифры, буквы).
