# Контракт ID-маркеров таблиц `<!-- t_pN_M -->`

Статус: утверждено (architect, t_6340b905). Реализация: coder (t_d50ff6ce).
Файл-источник кода: `firmware/src/create_markdown.py` (строки указаны приблизительно, по состоянию на
коммит `fc62e01`; при реализации ориентироваться на имена функций).

## 1. Цель

Исправить два дефекта привязки таблиц:

- **Дефект 1 (главный):** рассогласование ID-маркеров. Два механизма назначали id таблиц по разным
  сигналам и не сходились: `extract_table_images()` — по порядку `ta["tables"]` (boundingBox Yandex),
  `_inject_table_ids()` — по `page_boundaries` + порядковому номеру на странице в уже
  пост-обработанном MD. На границе страницы маркер съезжал на 1, AI-сверка резолвила маркер в
  чужой vision-эталон и LLM выдавал обрезанную/галлюцинированную таблицу.
- **Дефект 2:** `component_images` группировались по голому `table_num` из подписи. Номер «Таблица 2»
  не уникален между разделами/приложениями → три несвязанные таблицы склеивались в одну
  многостраничную, и `_merge_by_component_images()` удалял их блоки/маркеры.

**Направление (зафиксировано с пользователем):** id рождается в `parse_yandex_json_to_md()`
(единственное место, где `(page_idx, таблица)` доступны в том же порядке, что в вырезке);
группировка `component_images` по голому `table_num` удаляется, остаётся только spatial-pass
продолжений по геометрии.

Формат маркера НЕ меняется: `<!-- t_p{page+1}_{ti} -->`, отдельной строкой, ПЕРЕД подписью таблицы.
AI-этап `process_file` НЕ трогается (он уже парсит `re.findall(r"<!--\s*(t_p\d+_\d+)\s*-->", chunk)`).

       2b. _inject_table_ids(md, boundaries, table_images)   ← ПЕРЕСЧЁТ id (источник дефекта 1)

`_inject_table_ids()` (≈2711) заново нумерует таблицы: страница определяется по `page_boundaries`

ДО `merge_tables` (шаг 2), а `merge_tables` удаляет строки (дубли заголовков/данных продолжений) →
границы устаревают, таблицы у границ страниц маппятся неверно, индекс съезжает на 1.
Живой пример: «Таблица 2» Приложения 2 (ГОСТ 18410-73) получила маркер `t_p23_0` вместо `t_p23_1`;
`vision_tables["t_p23_0"]` = «Таблица 1» (допустимые токи) — чужая таблица.

## 4. Тождество id: доказательство

**Утверждение.** Для каждой страницы `page_idx` и каждого индекса `ti` в `ta["tables"]` маркер,
эмитированный `parse_yandex_json_to_md()`, равен id из `extract_table_images()` для той же пары
`(page, таблица)`.

**Доказательство.**
1. `process_file` передаёт ОДИН И ТОТ ЖЕ объект `pages` в `parse_yandex_json_to_md(pages=pages)`
   (≈5159) и в `extract_table_images(pdf_path, pages, img_dir)` (≈5195).
2. Обе функции итерируют `pages` одинаково: `for page_idx/page in enumerate(pages)` и
   `for pi, page_data in enumerate(pages)` → одна и та же страница получает одинаковый номер.
3. На странице обе обращаются к `ta = page["result"]["textAnnotation"]` и
   `raw_tables = ta["tables"]` — один и тот же список-объект.
4. `extract_table_images` назначает `ti` как позицию таблицы в `enumerate(ta["tables"])`
   (≈1726, 1758): это ИНДЕКС В МАССИВЕ Yandex, не Y-позиция.
5. `parse_yandex_json_to_md` обязан использовать ТОТ ЖЕ индекс: индекс таблицы в `raw_tables`
   (см. §5.1). НЕ порядковый счётчик Y-сортировки и НЕ позиционный номер в MD.
6. Следовательно `t_p{page_idx+1}_{ti}` == `t_p{pi+1}_{ti}`. ∎

**Гарантия реализации (§5.1):** индекс таблицы в `raw_tables` должен вычисляться по тому же списку,
что итерирует вырезка. Варианты:
- (рекомендуется) перед циклом рендера построить `table_raw_index = {id(t): i for i, t in enumerate(raw_tables)}`
  и в ветке `etype == "table"` брать `ti = table_raw_index.get(id(data))`;
- (альтернатива) расширить кортеж элементов до 4 полей: `(y, "table", table, raw_index)`
  и распаковывать его в цикле рендера.

**Допустимые расхождения (оба деградируют штатно, без ошибок):**
- (а) таблица есть в `tables[]` и вырезается, но `_table_to_md()` вернул пусто (`cells` нет /
  <2 строк после удаления примечания): в parse маркер НЕ эмитится, в `vision_tables` id существует,
  но ни один чанк его не запрашивает → не используется. Не регрессия (сегодня то же поведение).
- (б) у таблицы нет boundingBox (<4 вершин): вырезка пропускает её, parse рендерит и эмитит маркер;
  в `vision_tables` id нет → AI-этап пропускает (маркер попадает в «неснятые» warning). Не регрессия.

## 5. Изменения по функциям

### 5.1 `parse_yandex_json_to_md(pages=None, json_path=None) -> tuple[str, list[dict], list[tuple[int,int]]]`

Сигнатура и возвращаемое значение НЕ меняются. Меняется содержимое `md_text`.

В цикле рендера страницы (ветка `elif etype == "table":`, ≈615-623), для каждой таблицы,
которая реально отрендерена (`md_table` непустой), вставлять маркер ПЕРЕД строкой подписи:

```python
elif etype == "table":
    md_table, note_text = _table_to_md(data)
    if md_table:
        caption = _find_table_caption_for(blocks, data, raw_tables)
        page_lines.append(f"<!-- t_p{page_idx + 1}_{ti} -->")   # ti = индекс в raw_tables
        if caption:
            page_lines.append(f"*{caption}*")
        page_lines.append(md_table)
        if note_text:
            page_lines.append(f"> {note_text}")
```

- `ti` — индекс в `ta["tables"]` (см. §4), НЕ счётчик по Y и НЕ позиция в `page_lines`.
- Маркер эмитится ВСЕГДА (и без `--ai`): это осознанное изменение вывода (см. §9, R-1).
- Маркер вставляется ДО подписи; если подписи нет — непосредственно перед строками таблицы.
- `page_boundaries` считаются по финальному тексту страницы (с маркерами) — самосогласовано.

### 5.2 `_stitch_continuation_tables(md_text, page_boundaries=None, page_has_continuation=None) -> str`

БЕЗ изменения кода. Становится marker-aware по построению: для таблиц-продолжений код добавляет в
результат только `data_lines` и НЕ добавляет `lines[prev_end:t_start]` (≈1200-1202), т.е. маркер и
подпись продолжения глотаются вместе с подписью. Маркер первой таблицы (в `lines[0:t_start]`)
сохраняется. Требуется ПОДТВЕРДИТЬ тестом (§10, T6).

### 5.3 `extract_table_images(pdf_path, pages, img_dir) -> list[dict]`

Сигнатура и формат элементов НЕ меняются. УДАЛИТЬ блок ≈1768-1777 (table_num-группировку,
«Сначала сохраняем старое связывание по номеру таблицы»). ОСТАВИТЬ spatial-pass ≈1779-1815 целиком:

- продолжение — таблица без `caption`/`table_num` (has_caption == False);
- первая на странице (`ti == 0` в списке страницы);
- предыдущая страница существует, её ПОСЛЕДНЯЯ таблица — последний член текущей группы;
- нижняя грань предыдущей таблицы ≥ 90% высоты страницы (таблица упирается в низ) → продолжение.

Поле `item["table_num"]` (≈1753-1763) можно сохранить как диагностическую метаданную —
оно остаётся в `table_images.json`; группировка по нему ЗАПРЕЩЕНА (INV-6).

### 5.4 `_inject_table_ids(md_text, page_boundaries=None, table_images=None) -> str`

**УДАЛИТЬ ФУНКЦИЮ ПОЛНОСТЬЮ** (вместе с вызовом). Это первоисточник дефекта 1: пересчёт id по
производным сигналам (строки MD + устаревшие границы) вместо авторитетного `(page_idx, ti)` из JSON.
Вариант no-op отклонён: мёртвый параметр/вызов провоцирует путаницу и дублирование источника истины.
Сопутствующее: `_table_id_sort_key()` (≈2803) ОСТАЁТСЯ — его использует AI-этап (≈5308).

### 5.5 `run_script_postprocess(md_text, img_dir, page_boundaries=None, table_images=None) -> str`

- Сигнатура: **убрать параметр `page_boundaries`** (после удаления `_inject_table_ids` он нигде не

- Удалить шаг 2b (≈2949-2951).

### 5.6 `process_file(...)`

- Гейтинг `table_images if use_ai else None` СОХРАНИТЬ (минимальное изменение). Опциональное

## 6. Жизненный цикл маркера через склейки (ответ на открытый вопрос 1)

Три механизма склейки и их маркер-семантика:

| Механизм | Где | Marker-aware? | Как |
|---|---|---|---|
| 1. `_stitch_continuation_tables()` | внутри parse | да (по построению, без правок) | маркер+подпись продолжения лежат в `lines[prev_end:t_start]`, который для продолжений не добавляется в результат; маркер первой таблицы сохраняется |
| 2. `merge_tables()` (шаг 2) | run_script_postprocess | да (по построению, без правок) | при слиянии в `result` не добавляются `lines[t_end:n_start]` поглощаемых таблиц — их маркеры и подписи глотаются; маркер первой таблицы группы сохраняется |
| 3. `_merge_by_component_images()` (шаг 2c) | run_script_postprocess | да (уже реализовано) | `replacements` для `parts[1:]` = `(marker, end, [])` — блок удаляется; первый маркер остаётся (≈2900-2902) |

**Требование INV-4 выполняется во всех трёх путях:** у финальной MD-таблицы остаётся ровно один
маркер — маркер самого раннего компонента (первого по порядку страниц/строк).

**Вердикт по избыточности.** В рамках данного контракта НИ ОДИН механизм не удаляется:
- механизм 1 — единственный, работающий на этапе parse (чинит `raw.md` до vision);
- механизм 3 — единственный, использующий геометрический ground truth (`component_images`) и
  работающий после вырезки;
- механизм 2 — текстовая эвристика, частично избыточна с 1 и 3, но покрывает единственный кейс,
  который не ловят ни 1 (нет сигнала «Продолжение»/page_has_continuation), ни 3 (у продолжения ЕСТЬ
  подпись → spatial-pass требует has_caption=False): продолжение с повторной подписью «Таблица N»
  без ключевого слова. Кандидат на удаление — `merge_tables()` — ПОСЛЕ корпусной валидации, что
  реальные документы не дают этого кейса; в текущий объём не входит.

## 7. Инварианты

- **INV-1 (единый источник id):** каждый id `t_pN_M` в `md_text` соответствует ровно одной паре
  `(page_idx = N-1, table_index = M)` из `ta["tables"]` и равен id вырезки `extract_table_images()`
  для той же пары.
- **INV-2 (формат):** маркер — отдельная строка `<!-- t_p{page+1}_{ti} -->`, без текста на той же
  строке; вставляется ПЕРЕД подписью таблицы (или перед строками таблицы при отсутствии подписи).
- **INV-3 (уникальность в parse):** в `md_text` из parse каждый маркер встречается один раз;
  id уникальны (в пределах страницы `ti` уникальны по построению массива).
- **INV-4 (один маркер на финальную таблицу):** после всех склеек у каждой финальной MD-таблицы
  ровно один маркер — маркер первого компонента; маркеры поглощённых компонентов удаляются.
- **INV-5 (соответствие vision):** при AI-сверке `vision_tables[id]` — вырезка ТОЙ ЖЕ
  `(page, table_index)`, что и маркер; никогда не чужая таблица с тем же номером подписи.
- **INV-6 (component_images):** `component_images` формируется ТОЛЬКО spatial-pass'ем
  (без caption, первая на странице, предыдущая страница упирается в низ ≥90%). Голый `table_num`
  не группирует. Одноимённые таблицы разных разделов никогда не попадают в одну группу.
- **INV-7 (RAG):** `image_path`/`image_paths` таблиц в `rag_assets.json` привязываются по маркеру
  через `table_images.json` или по содержимому; маркерный путь НЕ зависит от `_inject_table_ids`.

## 9. Риски и ограничения

- **R-1 (маркеры видны в .md без --ai).** Раньше маркеры вставлялись только при `--ai`; теперь они
  есть в `md_text` из parse всегда. Это HTML-комментарии (невидимы при рендере) и дают RAG-привязку
  даже без `--ai` (плюс). Если требуется «чистый» .md без служебных комментариев — отдельный шаг
  вычистки вне данного контракта.
- **R-2 (продолжение с подписью теряет компонент).** После удаления table_num-группировки
  продолжение, у которого Yandex выдал подпись («Продолжение таблицы N»), имеет
  `has_caption=True` → spatial-pass его НЕ группирует (нужен caption-less). MD-склейка всё равно
  происходит (механизмы 1/2), но `image_paths` в RAG-реестре у склеенной таблицы будет только из
  первого компонента. На корпусе СП89/ГОСТ продолжения без подписей, поэтому не проявляется.
  Если появится — расширить spatial-pass условием «подпись совпадает с table_num головы группы
  И геометрия соблюдена» (опция, вне контракта).
- **R-3 (устаревшие page_boundaries после stitch).** `_stitch_continuation_tables` удаляет строки
  ПОСЛЕ вычисления `page_boundaries`; границы устаревают. Раньше это ломалось в `_inject_table_ids`;
  после удаления последнего единственный потребитель границ в постобработке исчезает
  (`_insert_images_into_md` параметр не использует), остаётся внутреннее использование в самом
  stitch (корректно — он работает с исходным массивом строк).
- **R-4 (опция: гейтинг 2c).** Сейчас `table_images` в `run_script_postprocess` передаётся только
  при `use_ai`; без `--ai` шаг 2c не выполняется и многостраничные таблицы остаются раздельными.
  Рекомендуемое (но НЕ обязательное в этом контракте) улучшение — передавать `table_images` всегда:
  spatial-pass детерминирован и склейка без AI полезна. Требует отдельной проверки на регрессиях.
