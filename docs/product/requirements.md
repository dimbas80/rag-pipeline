# interface_RAG — Требования

> Статус: требования согласованы с пользователем 2026-08-27. Реализация НЕ начата
> (ждём явной команды «старт» от пользователя).
>
> Источник: заметка Obsidian «Веб-интерфейс пайплайнов (план)» + ответы пользователя
> на вопросы оркестратора. Журнал решений — `docs/product/decision-log.md`.

## 1. Цель

Веб-страница (LAN) — оркестратор поверх двух существующих пайплайнов:

1. **Добавление документа**: загрузка файла → регистрация (`<stem>_reg.yaml`) →
   конвертация `create_markdown_ya` (OCR → MD + `image/` + `<stem>_chunks.jsonl` +
   `<stem>_assets.json`) → индексация `build_search_index` (Qdrant).
2. **Настройки**: управление конфигами обоих пайплайнов и Telegram-бота
   (провайдеры, роли, узлы графа, ключи) с валидацией и бэкапом.
3. **Чат**: окно поиска по базе — переиспользует `qa_graph.py` как библиотеку
   (как Telegram-бот).

## 2. Управляемые пайплайны (не изменяем)

| Репозиторий | Ключевые файлы | Назначение |
|---|---|---|
| `Create_Markdown_YA` | `firmware/src/create_markdown.py`, `create_markdown_config.yaml`, `providers.yaml` | PDF/DOCX/DOC → MD (Yandex Vision OCR), опц. AI-постобработка, RAG JSONL |
| `Build_Search_index` | `firmware/src/create_index.py`, `qa_graph.py`, `search.py`, `search_config.yaml`, `providers.yaml` | Индексация в Qdrant, QA-граф чата |

CLI `create_markdown.py`: `-i <file>` (OCR→MD), `--ai` (AI-постобработка),
`--rag` (RAG из MD), `--reg` (регистрация, интерактивный TTY).

## 3. Решение по структуре

- Папйплайны **не сливаем** — остаются отдельными репозиториями со своими досками
  и `STATE.md`.
- `interface_RAG` — **тонкий веб-оркестратор** поверх CLI обоих пайплайнов.
  Паттерн как у Telegram-бота (отдельный слой к `qa_graph.py`).

## 4. Стек

- **FastAPI** + WebSocket/SSE + статический HTML/vanilla JS (без Node/React).
- Запуск пайплайнов: `subprocess` **списком argv (без shell)**, лог + стриминг
  прогресса в браузер + история джобов.
- Три раздела UI: **Чат**, **Добавить документ**, **Настройки**.

## 5. UI — описание разделов

### 5.0 Общее (шапка и оформление)

- Фавиконка (иконка во вкладке браузера) + `<title>` с понятным названием.
- Заголовок и подзаголовок на странице: что это за инструмент и для чего
  (оркестратор пайплайнов OCR→Markdown и семантического поиска по базе ГОСТ).
- Аккуратное единообразное оформление всех трёх вкладок (единый стиль, шрифты,
  отступы, цвета). Без сырых дампов конфигов в интерфейсе.

### 5.1 Чат

- Поле ввода запроса + поле ответа.
- Вывод изображений (рисунков, таблиц) из `image/` документов — по аналогии с
  Telegram-ботом, с цитатами.
- Кнопка/команда «показать документы в базе» — список по **distinct-метаданным из
  Qdrant** (решение №7).

### 5.2 Добавить документ (одна страница, визуальные области)

Раздел — **одна страница** с тремя визуальными областями (НЕ пошаговые модальные
окна/wizard): **загрузка**, **регистрация** (форма с полями), **лог/прогресс**.

**Gating (решение №4).** Кнопки следующих шагов активны только после завершения
предыдущего. «Добавить в базу» активна **только при наличии `.md` и
`<stem>_reg.yaml`** — иначе показывать пользователю сообщение «завершите предыдущие
шаги».

- **Шаг 1 — Загрузка.** Кнопка «добавить документ» → выбор файла; загрузка в
  `/mnt/sdb/!База_ГОСТ/` (путь задаётся в настройках). После загрузки скрипт вырезает
  первую страницу и отдаёт её vision-модели с промптом на определение полей формы
  «регистрация документа»; определённые поля попадают в область регистрации.
- **Шаг 2 — Регистрация (отдельная область с полями, НЕ пошаговые окна).** Одна
  статичная область-форма со всеми полями `<stem>_reg.yaml`. Определённые vision —
  заполнены и редактируемы; обязательные поля помечены. Над каждым полем — русское
  название + **комментарий** (назначение и пример, tooltip/подсказка). Внутри пустого
  поля — имя поля из `<stem>_reg.yaml` (`document_id` и т.п.). Кнопка
  «Зарегистрировать документ» — внизу области → пишет `<stem>_reg.yaml` в папку
  документа.
- **Шаг 3 — Конвертация.** Кнопка «Конвертировать в Markdown» → `create_markdown_ya`
  с `--ai`; в логе идёт выполнение; по завершении — ссылка на `.md` для скачивания/
  просмотра (вьювер MD).
- **Шаг 4 — Добавить в базу.** Кнопка «Добавить документ в базу» → проверить
  `<stem>_reg.yaml`, запустить `create_markdown_ya` с `--rag` (чанкование), затем
  `create_index.py` (индексация). При наличии готового `.md` — не переконвертировать,
  идти из готового Markdown.
- **«Стоп»** — прерывает запущенный локальный процесс. Облачная задача Yandex OCR
  может не прерваться — принимается (решение №2).
- Кнопки «Конвертировать» и «Добавить в базу» неактивны, пока не внесены настройки
  (API-ключи, модели и т.п.).
- Лог: процесс конвертации и индексации; ошибки/предупреждения подсвечиваются цветом.

### 5.3 Настройки

Управление всеми конфигами обоих пайплайнов и Telegram-бота. API-ключи **не
отображаются**, но их можно удалить/добавить (маскирование). **Сырые конфиги
(`providers.yaml`/`.env`/прочее) в интерфейсе НЕ показываются** — только
структурированные поля.

- **Общий вид.** Вверху — единая кнопка **«Сохранить»** (записывает все секции одним
  действием) и кнопка **«Обновить»** (запрос к провайдерам и обновление списка
  моделей). НЕ показывать конфиг-дампы и НЕ делать отдельную кнопку сохранения на
  каждую секцию.
- **Yandex OCR** (ключи/настройки OCR).
- **Провайдеры.** Кнопка «Добавить провайдера» → окно с полями: имя, api key,
  base_url. Кнопки «Тест» (запрос списка моделей), «Добавить» (записать провайдера
  + модели с тегами в `providers.yaml`), «Отмена». **При добавлении — сканировать
  список моделей провайдера и дополнить `providers.yaml` с соответствующими тегами**
  (тег — **по имени модели**) (решение №5).
- **Раскрывающиеся секции выбора провайдера/модели**: chat (основная чат-модель),
  vision, embedding, rerank. В каждой секции — **подпись «Основная модель»** и
  **чекбокс «Fallback»**: настройки fallback видны только при включённом чекбоксе.
  У каждой секции — **пояснение**, что такое chat/vision/embedding/rerank
  (tooltip/подпись с назначением роли). В списках vision/embedding/rerank — только
  модели с соответствующим тегом.
- **Один провайдер** для `ai_postprocess` и `query_processing`: пользователь выбирает
  основную чат-модель — интерфейс пишет её как дефолт в обе роли **синхронно**
  (решение №6).
- **Vision-модель — синхронно в обе vision-роли**: выбранная vision-модель пишется в
  `create_markdown.table_vision` И `create_markdown.registration_vision`; отдельного
  селектора «регистрация» нет (решение №9).
- **Параметры узлов графа** (`search_config.yaml`: `analyze_query`,
  `reformulate_query`, `ask_clarification`, `generate_answer`) — с комментариями о
  назначении каждого узла.
- Кнопка **«Сохранить»** (единая) — запись в соответствующие конфиги пайплайнов.
  `.env` — общий.

## 6. Карта конфигов (актуальные имена)

| Файл | Проект | Назначение |
|---|---|---|
| `providers.yaml` | оба (`firmware/src/`) | реестр провайдеров (`base_url`, `api_key_env`, модели с тегами `chat`/`vision`/`embedding`/`rerank`) + роли |
| `create_markdown_config.yaml` | Create_Markdown_YA | промпты + RAG-секции |
| `search_config.yaml` | Build_Search_index | параметры узлов графа (`analyze_query`, `reformulate_query`, `ask_clarification`, `generate_answer`) |
| `.env` | общий (`firmware/src/`) | ключи: `YANDEX_*`, `DEEPSEEK_API_KEY`, `PROVOD_API_KEY`, `ANYMODEL_API_KEY`, `Z_AI_API_KEY`, `SILICONFLOW_API_KEY`, `TELEGRAM_BOT_TOKEN` |

Роли в `providers.yaml`: `create_markdown.table_vision` / `ai_postprocess`,
`build_search_index.query_processing` / `embedding` / `rerank`.

## 7. Ключевые технические решения

- **`--reg` (TTY) в вебе не работает.** После выбора/загрузки файла запускается
  скрипт, вырезающий первую страницу → vision-модель с промптом определения полей
  формы «регистрация документа». Неопределённое заполняет пользователь. Веб сам
  пишет `<stem>_reg.yaml` (per-doc схема уже поддержана `load_rag_config`).
  Пайплайн не меняем.
- **Qdrant**: `create_index.py` требует абсолютный
  `--qdrant-path /mnt/sdb/!База_ГОСТ/Markdown/qdrant_data` + `--strict`.
- **Чат**: импорт `qa_graph.py` (QAGraph run/stream), вывод цитат и картинок таблиц
  как в Telegram-боте.
- **Пути не хардкодить** — конфиг деплоя (dev-значения здесь, prod-значения на LXC).
- **Запись в Qdrant выполняет только прод-инстанс** (решение №3).

## 8. Деплой

- Разработка — `/root/projects/interface_RAG`; прод — **LXC `192.0.2.21`**
  (порт 80, LAN, без авторизации). Все тесты и приёмка — на LXC.
- **Чистая структура на проде** — только пайплайны, веб-интерфейс и общие конфиги,
  **без** `.git/`, `docs/`, `workflows/`, `.hermes/`, тестов и прочих артефактов
  разработки. Деплой копирует только нужное (`firmware/src`, статика, конфиги).
- **Единый общий конфиг.** Один `providers.yaml` и один `.env` (плюс
  `create_markdown_config.yaml`, `search_config.yaml`), в которые пишет интерфейс.
  Пайплайнам конфиг **передаётся через CLI-ключи** (`--providers-config`, `--config`
  и т.п.), ключи `.env` инжектируются в окружение subprocess. У пайплайнов нет своих
  копий конфигов.
- Qdrant: bind-mount `/mnt/sdb` → база одна, источник истины не раздваивается;
  **запись — только прод**.
- Деплой: rsync/копирование нужных файлов → venv + зависимости → systemd-юнит →
  smoke-тест (добавить документ → проверить индекс → задать вопрос в чате).

## 9. Открытые под-вопросы (для архитектора, не блокируют старт)

- Схема `<stem>_reg.yaml` и публичный интерфейс `qa_graph.py` — reverse-engineer на
  discovery-этапе.
- Тег модели (`chat`/`vision`/`embedding`/`rerank`) при «добавить провайдера» —
  **по имени модели** (решение №5). Архитектору: задать правила матчинга имён.
- Роль vision-модели для «регистрации документа»: отдельная роль или переиспользовать
  `table_vision`.
- Fallback-поведение, если vision ничего не распознал (первая страница без текста,
  не-ГОСТ документ).
- Dev-порт (по умолчанию 8081; 8080 занят dashboard).
